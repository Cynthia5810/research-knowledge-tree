# 分类原则与边语义

> 本文档是知识树的「宪法」：每次批量导入概念后，按此审查。机械项由 `npm run lint:ontology` 检查，语义项由 AI 挑刺 + 用户裁决。

## 1. 六大类别的成员资格判据

| category | 判据：节点回答的问题 | 例 | 反例 |
|---|---|---|---|
| object 研究对象 | 它是被研究/被处理的东西吗？ | 盐湖卤水、电池废料 | — |
| material 材料 | 它是构成功能器件的物质体系吗？ | 聚酰胺膜、双极膜 | 仿生（是设计范式） |
| method 方法 | 它是人执行的过程/工艺/策略吗？ | 纳滤、湿法浸出、表面正电化 | — |
| mechanism 机制 | 它是自然发生的物理化学原理吗？ | Donnan 排斥、尺寸筛分 | — |
| performance 性能 | 它是可度量的指标吗？ | Li-Mg 选择性、比能耗 | — |
| application 应用 | 它是要完成的任务/场景/流程环节吗？ | Li-Mg 分离、卤水管理 | — |

## 2. 命名与分类的核心原则

1. **同一父节点下的子类尽量用同一判据划分**；若领域习惯混用（如膜类按"赋予选择性的特征"命名：材质/配体/通道设计/功能），允许保留习惯名称，但必须用关系边显式补全本质：
   - 凡按功能或设计范式命名的类，**必须挂 `acts_via` 指明机制**（例：仿生通道膜 → 人工离子通道）。
   - 树形分支负责导航（贴近文献用语），机制边负责本质（支撑跨分支追溯）。
2. **一个概念只建一个节点**：同义词写进 `aliases`，不另建节点（Donnan 排斥 vs 静电排斥这类"具体形式 vs 一般原理"用 `is_a` 表达，不算同义词）。
3. **定义必须能把节点和它的兄弟节点区分开**，否则说明分类有问题。

## 3. 关系边语义表

| 边 | 读法 | 方向约定 | 备注 |
|---|---|---|---|
| `is_a` | X 是一种 Y | 子→父 | 同时写入 frontmatter `parent`；禁止循环 |
| `component_of` | X 是 Y 的组成部分 | 部分→整体 | **当前双义**：物理部件（膜→电渗析）与流程环节（预处理→锂回收）。暂时接受，节点规模扩大后评估拆分 `step_of` |
| `made_of` | X 的材质是 Y | 器件→材料 | |
| `has_property` | X 具有性质 Y | 实体→性能 | |
| `prepared_by` | X 由 Y 制备/产生 | 产物→方法 | 含"是…的产物"（电池浸出液 → 湿法浸出） |
| `used_for` | X 用于 Y | 手段→任务 | |
| `acts_via` | X 通过机制 Y 起作用 | 实体/方法→机制 | 功能命名类的强制边（见原则 2.1） |
| `improves` | X 改善 Y | 手段→性能 | |
| `related_to` | 弱关联 | 双向 | 仅当以上都不贴切时使用；审查时优先升级为强语义边 |

## 4. 导入后审查清单（AI 挑刺用）

- [ ] 新节点的 category 是否符合第 1 节判据？
- [ ] 同层兄弟节点是否混用分类判据？混用的是否都补了 `acts_via`？
- [ ] 有没有应该合并的近义节点？有没有一个名字两个概念？
- [ ] `related_to` 边里有没有可以升级为强语义边的？
- [ ] 定义是否能区分兄弟节点？
- [ ] 机械项：`npm run lint:ontology` 通过？
